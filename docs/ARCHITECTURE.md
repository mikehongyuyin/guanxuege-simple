# 观学阁 · 架构设计说明

> 面向 Java 后端岗位的工程设计说明。重点不是"用了什么"，而是"为什么这么选"。

---

## 一、整体形态

单体应用（Monolith），前后端分离，容器化部署。

```
┌──────────────────┐
│  Vue 3 (Vite)    │  :8088（容器内 80）
└────────┬─────────┘
         │  /api/**
         │  Nginx 同域反代 —— 无跨域，无 CORS 预检开销
┌────────▼───────────────────────────────────────┐
│  Spring Boot 单体  :8080                      │
│                                               │
│  Controller → Service → Mapper → MySQL        │
│       │                                       │
│       └─ 横切：鉴权 / 归属校验 / 缓存 / 异常处理 │
└───────────────────────────────────────────────┘
                    │
              Caffeine（进程内）
```

**为什么不上微服务**：见 [ADR-001](ADR-001-微服务重构为单体.md)。核心结论是——
在单机、单团队、中等复杂度的前提下，微服务引入的分布式复杂度换不来对等的收益。

---

## 二、分层与职责

| 层 | 职责 | 约定 |
|---|---|---|
| Controller | 参数接收、归属校验、调用 Service | 不写业务逻辑；从 `X-User-Id` 取当前用户 |
| Service | 业务逻辑、事务边界 | `@Transactional` 标注在写操作上 |
| Mapper | 数据访问 | MyBatis-Plus `BaseMapper`，复杂查询用 Wrapper |
| Entity / VO / DTO | 数据载体 | Entity 对应表，VO 出参，DTO 入参 |

Controller 不直接碰 Mapper，保证业务逻辑可测、可复用。

## 三、模块划分

按**业务边界**分包，而不是按技术分层分包 —— 每个包内部自成一套 Controller/Service/Mapper/Entity。

```
com.guanxuege
├─ common      横切能力：R、全局异常、JWT、缓存、过滤器、词库、归属校验
├─ auth        账户：用户、孩子、家庭档案、同意记录、社区资料与隐私
├─ learningplan 学习计划：计划、任务、打卡、亲子契约
├─ grade       成绩记录与趋势
└─ community   社区：帖子、评论、点赞、圈子、话题、@提及
```

> **社区维度**：育儿社区与心声社区共用 `community` 模块，靠 `gx_post.community` /
> `gx_circle.community` 切分（`parenting` / `voice`），而不是各建一套服务。

这样做的收益是：模块内聚，未来若真要拆分服务，可以直接按包切分，不需要重写。

## 四、横切机制

### 4.1 鉴权：JWT + 过滤器

```
请求 → JwtAuthenticationFilter
         ├─ 白名单路径（登录/注册/静态资源）→ 放行
         ├─ 解析 Authorization: Bearer <token>
         ├─ 校验签名与过期
         └─ 注入 X-User-Id 请求头 → Controller
```

失败统一返回 `401`。密钥取自环境变量 `JWT_SECRET`（>= 32 字符），
未配置时回退内置默认值并打印 `[SECURITY]` 告警 —— 保证开发零配置，同时生产不会静默使用弱密钥。

### 4.2 授权：归属校验（本项目的安全核心）

**鉴权解决"你是谁"，授权解决"这是不是你的"。** 两者缺一不可。

```java
// 用法：Controller 中先校验，再做业务
ownershipService.requireChild(userId, childId);
```

校验链路：

```
task → plan → child → parent_id == 当前 userId
```

失败抛 `ForbiddenException` → HTTP **403**。

这里有一个刻意的语义区分：

| 场景 | 返回 | 理由 |
|---|---|---|
| 参数缺失、业务规则不满足 | 400 | 用户操作问题 |
| 访问他人资源 | **403** | 安全事件，需独立监控告警 |

如果越权也返回 400，监控就无法从海量 400 里识别出攻击行为。

更新类接口还会**强制回填归属字段**，防止通过改 `parentId` 把资源过户到别的账号。

### 4.3 缓存：Caffeine

进程内缓存，用于用户摘要信息（帖子列表里的作者昵称/头像），避免 N+1 查询。10 分钟过期。

选 Caffeine 而非 Redis：单机单体下，本地缓存无网络开销、无额外运维成本；
代价是多实例部署时缓存不共享 —— 这是接受单体架构时同步接受的取舍。

### 4.4 异常处理

`@RestControllerAdvice` 全局兜底，业务异常转统一结构 `R { code, message, data }`。

### 4.5 内容安全

两级词库，帖子与评论共用：

- **违禁词**（16 个）→ 拒绝发布
- **焦虑词**（14 个）→ 放行 + 标记 + 返回温和提示

### 4.6 分布式 ID

雪花算法，`datacenterId` / `workerId` 由容器网卡信息自动推导，
避免多实例部署时手动配置 ID 冲突。

## 五、关键不变量（Invariant）

这些是系统必须始终成立的性质，也是单元测试重点守护的对象：

| 不变量 | 保障手段 |
|---|---|
| 同一任务同一天只能打卡一次 | `uk_task_date(task_id, date)` 唯一键 |
| 点赞对同一用户幂等，不重复计数 | `uk_post_user(post_id, user_id)` 唯一键 |
| 点赞计数在并发下不丢失更新 | 数据库原子自增 |
| 用户不能读写他人孩子的数据 | `OwnershipService` 链路回溯 + 403 |
| 更新操作不能改变资源归属 | 强制回填归属字段 |
| 未声明监护关系不能添加孩子 | 强同意门禁 |

## 六、已识别的技术债

诚实地列出来，便于评估当前状态：

1. **缓存无失效联动** —— 用户更新昵称后，帖子列表里的作者信息要等 10 分钟才刷新
2. **计数依赖事务隔离** —— 点赞计数虽已原子化，但热度榜单仍是读时计算，数据量大后需预计算
3. **缺少可观测性** —— 未接入 Actuator / 指标采集 / 结构化日志
4. **词库硬编码** —— 词库写在工具类里，运营无法自助维护
5. **无集成测试** —— 当前只有单元测试，无端到端验证

每一项都对应 README 中的后续规划。
