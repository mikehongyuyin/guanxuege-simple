# ADR-001：将微服务架构重构为单体应用

- **状态**：已接受（2026-08）
- **影响范围**：后端整体架构
- **相关文档**：[ARCHITECTURE.md](ARCHITECTURE.md)

---

## 背景

项目最初按微服务标准形态搭建：

| 组件 | 用途 |
|---|---|
| Spring Cloud Gateway | 统一入口、鉴权 |
| Nacos | 注册中心与配置中心 |
| OpenFeign | 服务间调用（如社区取作者信息） |
| RocketMQ | 异步事件（发帖后更新热度/话题） |

上线运行一段时间后，暴露出几个问题：

1. **运维成本与业务规模不匹配** —— 6 个容器进程，但日均请求量远未达到需要拆分的量级。一次本地全量启动要等好几分钟。
2. **分布式复杂度换不来收益** —— 服务间调用只发生在"社区模块查用户信息"这一处，而且完全可以用本地调用完成；消息队列只承载"发帖后更新热度"一件事，本身就是同步能做完的操作。
3. **排查路径变长** —— 一次发帖失败要看网关日志、服务日志、MQ 消费日志，本地复现成本高。
4. **团队协作前提不成立** —— 微服务的核心收益是"多团队独立发布"，而这是单人开发的项目，该前提根本不存在。

---

## 决策

**将后端重构为单个 Spring Boot 应用**，保留业务包结构，移除 Spring Cloud 相关组件。

具体做法：

- 网关鉴权 → 应用内 `JwtAuthenticationFilter`，仍向 Controller 注入 `X-User-Id`，**Controller 契约不变**
- Feign 远程调用 → 同进程注入 `UserService` 直接调用
- RocketMQ 异步事件 → 同步落库并更新热度/话题
- 缓存由 Redis 改为 Caffeine 本地缓存

**关键：按业务边界分包（`auth` / `learningplan` / `grade` / `community`），而非按技术分层分包。**
每个包内自成一套 Controller / Service / Mapper / Entity。

---

## 理由

1. **匹配真实约束** —— 单机部署、单人开发、中等复杂度。架构应当匹配约束，而非匹配潮流。
2. **显著降低运维与调试成本** —— 容器从 6 个降到 3 个，一次请求只在一个进程内流转。
3. **保留未来拆分的可能** —— 因为按业务边界分包，若将来真需要拆分，可以直接按包切分，
   不需要重写业务逻辑。这是这次重构中最重要的一条设计约束。
4. **减少故障点** —— 少一个中间件就少一类故障（网络分区、消息堆积、注册中心抖动）。

---

## 代价与风险

诚实记录这次决策换来了什么、失去了什么：

| 失去的能力 | 影响 | 缓解方式 |
|---|---|---|
| 模块独立扩缩容 | 无法只扩容社区模块 | 当前量级无此需求 |
| 缓存多实例共享 | 多实例部署时缓存不一致 | 当前为单机部署 |
| 服务级故障隔离 | 单模块 OOM 会拖垮整体 | 靠监控与资源限制兜底 |
| 异步削峰 | 突发流量直接打库 | 当前量级可接受 |

其中**异步削峰**是最实质的一笔损失。发帖热度计算改为同步后，
若未来社区写入量上升，需要重新引入消息队列或改为批量预计算。

---

## 何时重新评估

出现以下任一情况时应重新考虑服务化：

- 需要多团队并行开发、独立发布
- 某个模块的负载特征明显独立于其他模块（如社区读多写少、成绩统计计算密集）
- 单机资源已成为瓶颈
- 需要按模块设置不同的可用性等级

在此之前，保持单体是更经济的选择。

---

## 经验总结

> **中间件的价值来自它解决的问题，而不是它本身的先进程度。**
>
> 引入 Nacos 是为了解决"服务多了怎么互相发现"，引入 MQ 是为了解决"同步做不完/不能同步做"。
> 如果这两个前提都不成立，那它们就只是额外的故障点和运维负担。
>
> 判断架构好坏的标准不是"够不够分布式"，而是"复杂度是否花在了真正的瓶颈上"。
